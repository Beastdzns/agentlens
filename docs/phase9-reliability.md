# Phase 9 — Storage Reliability Report

Owner: **S** (Member 3 — Reliability Testing)

This report covers the reliability and performance characteristics of the
persistent (SQLite) storage backend added in Phase 9, and how they are
verified.

- Implementation: `src/agentlens/storage/db.py`, `src/agentlens/storage/sqlite.py`
- Store tests: `tests/test_storage_sqlite.py`
- Scenario tests: `tests/test_persistence_reliability.py`
- Benchmark script: `tests/benchmark_storage.py`

---

## 1. What is verified

| Property | How it is tested |
|---|---|
| **Fidelity** | Round-trip of UUIDs, timezone-aware datetimes, nested JSON, unicode, `None`, ~5 KB payloads (`test_event_round_trip_fidelity`). |
| **Ordering** | Events returned in `timestamp` order regardless of insert order (`test_get_trace_events_ordered_by_timestamp`). |
| **Concurrency** | 40 concurrent writers × 5 events = 200 events, plus a mixed read/write storm; no `database is locked` (`TestConcurrency`). |
| **Durability** | Close the database, reopen the same file, all events/traces intact (`TestDurability`). |
| **Migrations** | Fresh DB records exactly `0001`; re-running is a no-op; a staged `0002` applies once; an applied version is never re-run (`TestMigrations`). |
| **Parity** | The same workload produces identical results on SQLite and in-memory stores (`TestParityWithMemory`). |
| **Fail-open** | A broken store never crashes the agent — `EventCollector` warns and continues (`test_collector_is_fail_open_with_broken_store`). |
| **Restart (app-level)** | Repeated FastAPI lifespan start/stop cycles reuse the file and accumulate traces (`test_persistence_reliability.py`). |
| **Config** | WAL journal mode, `synchronous=NORMAL`, `busy_timeout=5000` are applied per connection (`TestConnectionConfig`). |

### Running the tests

```bash
./venv/bin/python -m pytest tests/test_storage_sqlite.py tests/test_persistence_reliability.py -q
```

Current result: **39 tests pass** (32 store-level + 7 scenario-level), part of
the full **272-test** Python suite; the **85 / 85** browser tests are
unaffected.

## 3. Findings

1. **Bulk writes are mandatory for ingestion.** Per-event writes pay one
   `fsync`/commit each; `save_events_bulk` collapses them into one transaction
   for an **11.7×** gain. The collector still calls `save()` per event (fine
   for the ~6-event demo runs); high-volume ingestion should batch.

2. **Keyset pagination keeps history queries flat.** SQLite latency is
   essentially constant (≈1.2 ms) from 1 k → 10 k traces because
   `(start_time, trace_id)` is indexed and each page is a `LIMIT` seek. The
   in-memory store must sort the whole table every call, so it degrades to
   ≈14 ms at 10 k — **the persistent backend is ~12× faster at scale**.

3. **WAL + a single serialised writer is enough.** All 40 concurrent writers
   completed with zero lock errors. The write connection is guarded by an
   `asyncio.Lock`; the 4-connection read pool serves readers concurrently with
   WAL. `busy_timeout=5000` is a safety net, not a hot path.

4. **The read pool must be reset on shutdown.** During this work we found and
   fixed a lifecycle bug: `init_db()` returned the cached singleton even after
   `Database.close()`, so a second start reused a closed database and
   deadlocked the read pool. `close_database()` now closes **and resets** the
   singleton; `test_repeated_start_stop_cycles_accumulate` is the regression
   guard.

5. **`get_trace` must hydrate events.** The `traces` table only stores the
   summary; events live in `events`. `SqliteTraceStore.get_trace()` now joins
   both so `GET /api/traces/{id}` returns payloads, matching the in-memory
   store (covered by `TestParityWithMemory` and `test_trace_and_events_survive_restart`).

## 4. Known limitations / follow-ups

- **Duplicate step events.** `_AgentRunner` routes pipeline steps through
  capture wrappers *and* records some events explicitly; the events table may
  contain duplicates relative to the intended per-step count. Not a storage
  bug, but worth deduplicating at the collector level.
- **Failed runs have no persisted trace on the live path.** A live Gemini
  failure returns HTTP 502 without a `trace_id`, so the UI can only show an
  error banner. Persisting the failed trace before responding would let the
  dashboard link to it.
- **Single-writer ceiling.** SQLite serialises writers. The current design is
  ample for the demo; if write volume grows, the same interfaces allow a
  drop-in PostgreSQL backend (`asyncpg`) without touching the API layer.
